# HashLab — Advanced Cryptographic Hash Behavior Analysis and Security Evaluation Platform

A runnable web application for comparing MD5, SHA-1, SHA-256, SHA-512, SHA3-256 and SHA3-512. It measures digest output, input mutation sensitivity, avalanche statistics, machine-specific performance, and file integrity.

## Features

- React + TypeScript dashboard with seven workspace sections.
- FastAPI backend using Python `hashlib`.
- Digest size and hexadecimal output comparison.
- Character, whitespace, byte and single-bit mutation experiments.
- Hamming distance and avalanche percentage.
- Repeated benchmark trials, median/mean/standard deviation and throughput.
- File hashing with 1 MiB streaming, saved local baselines and verification.
- SQLite storage for generated experiment records.
- CSV export of the full experiment table.
- Pytest API/unit tests.
- No hardcoded benchmark results; all measurements are generated at runtime.

## Requirements

- Windows 10/11
- Python 3.13 recommended (Python 3.12+ should also work if available)
- Node.js 20 LTS or newer, with npm
- VS Code optional but recommended

## Windows PowerShell setup

Extract `hashlab_project.zip` to a folder such as `C:\Users\<you>\Documents\hashlab_project`.

Open PowerShell in that folder:

### 1. Start the backend

```powershell
cd .\backend
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8001
```

If `py -3.13` is not installed, use `py -3.12` or `py -3` with a supported Python version. Leave this terminal open.

Backend API docs: http://127.0.0.1:8001/docs

If PowerShell blocks script activation, the commands above intentionally invoke the venv's Python executable directly; you do not need to run `Activate.ps1`.

### 2. Start the frontend in a second PowerShell window

```powershell
cd C:\Users\<you>\Documents\hashlab_project\frontend
npm install
npm run dev
```

Open the URL printed by Vite, normally http://127.0.0.1:5173.

### 3. Run backend tests in a third terminal

```powershell
cd C:\Users\<you>\Documents\hashlab_project\backend
.\.venv\Scripts\python.exe -m pytest -q
```

### 4. Build the frontend

```powershell
cd C:\Users\<you>\Documents\hashlab_project\frontend
npm run build
```

## First demo

1. Open Hash Explorer and hash `CyberSecurity123`.
2. Open Mutation Lab, choose “Flip one bit in a byte,” and run the experiment.
3. Open Avalanche Lab and run 100 trials per algorithm (or use a smaller number for a quick demo).
4. Open Benchmarks and run the default sizes `1,64,1024` KB.
5. Open File Integrity, choose a sample file, and save a baseline. Select the same file and verify for MATCH. Then modify a copy and verify for MISMATCH.
6. Open Dataset & Reports, generate records, and export CSV.

## Dataset interpretation

The application stores records in `backend/data/hashlab.sqlite3` (created automatically). The CSV export includes the measurements collected so far. The `seed` makes generated byte payloads and mutation-position selection reproducible, but elapsed times are machine- and load-dependent and are not expected to repeat exactly.

The default dataset-generation endpoint records:
- Controlled text/structured-input changes.
- Single-bit avalanche trials for each algorithm.
- Benchmark trials for 1 KB, 16 KB and 64 KB seeded payloads.

The separate Benchmark Lab supports larger configured sizes up to 10,240 KB and uses seven trials by default. The separate Avalanche Lab returns summary statistics and an approximate normal 95% confidence interval. For a research report, repeat the experiments over multiple independent baseline messages and report your environment.

## Important security notes

- MD5 and SHA-1 are included for historical comparison. Their collision resistance is broken; do not use them for new security-sensitive designs.
- SHA-256, SHA-512, SHA3-256 and SHA3-512 are modern general-purpose hash functions.
- Hashes are not encryption and do not authenticate a file's origin by themselves.
- A stored digest is useful for integrity verification only if the reference digest is trusted. This demo's SQLite baseline table is not tamper-proof.
- For passwords, use a password-hashing algorithm such as Argon2id, scrypt or bcrypt with salts. Do not store passwords as a plain fast SHA-256 digest.
- An avalanche result near 50% does not prove collision resistance or overall cryptographic security.

## Research methodology outline

1. Define controlled input mutations and a fixed baseline.
2. Generate digest outputs for all selected algorithms.
3. Compute Hamming distance between equal-length digests.
4. Calculate avalanche percentage as `changed_output_bits / digest_bits * 100`.
5. Measure repeated hash-computation times using `perf_counter_ns`; exclude payload generation from benchmark timing.
6. Report mean, median, standard deviation, throughput and sample size.
7. Compare results while discussing the limits of avalanche testing and timing benchmarks.
8. Export raw observations and retain seed, input size, runtime and trial count.

## Known scope limitations

This is an educational local prototype, not a hardened production service. It has no authentication, rate limiting, upload quota, multi-user access control, signed baselines, or forensic chain-of-custody controls. Do not expose the API to the public internet without additional security engineering.
